# x402 v2

Xarta is an x402 resource server. It uses the official Python SDK's x402 v2 HTTP,
EVM `exact`, EIP-3009, and USDC support. Base Sepolia (`eip155:84532`) is the
development network; Base (`eip155:8453`) is the production network.

## Payment Authority

The Base blockchain is the authoritative settlement record. Successful payment
evidence consists of the network, transaction hash, payer, payee, asset, amount, and
successful on-chain settlement. Xarta does not maintain a standalone PostgreSQL
payment ledger or a Dragonfly payment cache for the public x402 path.

Xarta is responsible for:

1. preparing and pricing the complete request;
2. issuing official `PAYMENT-REQUIRED` requirements;
3. authenticating the paid retry's terms and settling through the configured
   facilitator;
4. requiring a concrete transaction hash from a successful EVM settlement;
5. logging `x402_settlement_succeeded` with `network`, `transaction`, `payer`,
   `pay_to`, `asset`, `amount`, `resource`, and flow/request context;
6. executing the work only after successful settlement and logging;
7. returning the official `PAYMENT-RESPONSE` and normalized payment evidence in JSON
   receipts where appropriate.

Payment signatures, authorization payloads, private keys, seed phrases, and raw
environment values must never be logged. Transaction hashes and wallet addresses are
public chain identifiers.

## Signed Challenges

`PaymentPayload.accepted` is a client echo and is not price authority. Xarta places a
short-lived opaque JWT in `PaymentRequirements.extra.xartaChallenge`, signed with the
deployment's `X402_CHALLENGE_SIGNING_KEY`. It authenticates the complete server
requirements, resource, prepared-request semantic fingerprint, pricing revision, and
absolute quote expiry. A paid retry therefore does not require a database lookup and
cannot redefine price, recipient, network, asset, timeout, or request semantics.

The x402 `payment-identifier` extension remains required for protocol interoperability.
Xarta does not use that identifier as durable business identity, cache it, promise
indefinite paid-response replay, or reject all future reuse through local persistence.
A new valid authorization purchases a new execution even when request semantics match a
previous execution.

## Execution Modes

Payment does not change node execution mode. Synchronous work settles, logs, executes,
and publishes deterministic successors without creating PostgreSQL workflow state.

The root `NodeTask` carries bounded x402 admission evidence. Synchronous nodes only
propagate it. When a genuinely tracked node is accepted, its normal `node_executions`
row stores the admission object before the adapter runs. This makes the transaction hash
durable across worker handoff, callbacks, reconciliation, and restart for tracked or
irreversible work without creating a separate payment ledger.

## Failure Boundary

A facilitator rejection does not execute work or emit a successful-settlement event. A
timeout, connection failure, HTTP error, or malformed response is treated as an
uncertain settlement result, not proof that no on-chain settlement occurred. Xarta does
not rebuild a SQL uncertainty state machine; the client may need to inspect its
facilitator or chain context.

For a synchronous public request there is an unavoidable boundary:

```text
on-chain settlement succeeds
    -> Xarta receives and logs the response
    -> Xarta crashes before execution or JetStream acceptance
```

Xarta has no durable outstanding commercial-obligation record at that boundary. This is
an intentional tradeoff for low-cost deterministic synchronous operations. Tracked
irreversible workflows instead persist settlement admission provenance before the
external side effect proceeds. Refund behavior is a separate product capability.

## Retention

- Base settlement evidence follows public blockchain semantics.
- Structured application logs follow the deployment's operational retention policy.
- Generated artifacts follow their resource retention policy, such as 30 days.
- Tracked admission provenance follows workflow retention.
- Payment identifiers are not retained merely to provide replay.

Deleting an artifact does not delete its blockchain transaction.

## Non-Goals

- no standalone payment ledger;
- no Redis or Dragonfly payment/settlement cache;
- no indefinite payment-ID replay guarantee;
- no Xarta-specific payment smart contract;
- no private flow, document, customer, recipient, or request metadata on-chain.
